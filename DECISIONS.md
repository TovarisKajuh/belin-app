One line per significant decision: what, why, when.

- 2026-10-06: An address that already has an account gets the same "Preverite e-pošto" screen at signup as a new one and is told by email to sign in; the rate-limit answer ("Preveč poskusov" on the fourth try within the hour) is also the same for both. Reason: an on-screen difference would turn the form into a way to test whether an address has an account, which the login form deliberately prevents.

- 2026-10-06: The public signup form may send at most 25 mails per rolling 24 h (signup_confirm and signup_exists together), and each person at most 10 login links per rolling 24 h. Reason: Resend get-usage on 05.10 showed "Emails (daily): 0 / 100" resetting at 23:59:59Z and a 10 requests per second limit; without a cap one script against either form spends the whole day's mail and every login link, invite and signup confirmation fails until the reset.

- 2026-10-06: The VAT number is required at signup and validated by format; a number VIES does not know is allowed with a warning. Reason: reverse-charge invoices need the recipient's VAT ID, and VIES is down for some member states on some evenings (DE was on 05.10).

- 2026-10-06: Pilot terms are versioned (TERMS_VERSION) and the version and consent time are stored on the signup and on the organization. Reason: "which terms did this customer accept" must have an answer the day the terms change.

- 2026-08-12: A generated document path is written ONCE; regenerating a document means a new row and a new path. Reason: Supabase storage upsert returns success on an existing path while keeping the original bytes, its delete is eventually consistent so remove-then-upload races, and storage.download() serves a cached copy that can return the previous file after a genuine replacement. Where the CONTENT is what matters, reads go through a cache-busted signed URL, which is now true of both the seed verification and acceptPo re-hashing a naročilnica before binding an acceptance to it. Full reproduction in docs/known-issues.md entry 2.

- 2026-08-12: Every PDF render goes through renderDocument in lib/pdf/theme.tsx, which deletes and re-registers the font family first. Reason: @react-pdf shares one parsed font per family across renders in a process, and a later document introducing new glyphs gets a ToUnicode map that no longer matches the glyphs it draws. The page looks perfect while its text layer is corrupt, so the failure is invisible locally and appears only on warm servers. Our own nine day completion report copied as "Kraj" instead of "Kranj". Pinned by tests/pdf-font-subset.test.tsx, which must stay in its own file with small documents first, because a large document rendered first inoculates every document after it and hides the bug.

- 2026-08-12: Requesting finalization is its own office-only action on the subcontractor side, not a move on the shared status control (founder veto of the plan default). Reason: it is the act that starts the acceptance, so it must always notify the client, and leaving the same transition on the status control as well would give one state two doors of which only one told anybody. Withdrawing a request stays on the status control, because taking back your own request forms no contract. The demo seed also now stages sent and accepted naročilnice (second founder veto), made safe by rendering their real PDFs and hashes through the same code the app uses rather than writing rows no code path could have produced.

- 2026-08-12: The duplicate create_project_from_review overload is dropped, and p_roofs becomes a REQUIRED argument in lib/database.types.ts. Reason: "create or replace function" only replaces a function with an identical signature, so adding p_roofs on 2026-07-20 did not replace the older seven argument version, it created a second one beside it. Both the database and the repo carried both, which is why nothing looked wrong. Nothing called the old body because the wizard always sends p_roofs and PostgREST resolves overloads by argument name, but that is a one argument wide safety margin around a silent failure: a call omitting p_roofs would have created the project with its material list intact and its roofs missing, returning a normal project id with no error. Also recorded: the Supabase connector assigns its own version number when it applies a migration, so the numbers in the ledger will never equal the hand written prefixes in supabase/migrations/. The repo file order is the source of truth for REBUILD order, the ledger only records when each was applied; matching content, not matching numbers, is what has to be checked.

- 2026-07-19: Live sync is a contentless per-project broadcast ping, not a data channel. After any write, the server posts an empty ping to `belin:project:<id>` via the Supabase realtime broadcast REST endpoint; open clients re-run their server components through their own authorized reads. Nothing crosses the channel, so there is no data to leak and no client-side merge to get wrong; the server stays the single source of truth. The primary REST endpoint was verified working (HTTP 202); the documented fallback (realtime.send inside the RPCs plus triggers) exists (realtime.send confirmed present) but is not needed. Accepted debt: the channel is public and its topic is derivable from the project UUID, which already appears in signed photo URL paths, so a holder of the anon key plus a UUID could both listen for and inject pings. A forged ping only makes clients re-fetch through authorized reads (no data exposure, no writes) and the client debounce caps the rate, so this is a bounded refresh-amplification surface, accepted for the PoC. Private channels with realtime authorization arrive with real auth in phase 3.

- 2026-07-19: The material check first-gate is escapable ("Material še ni prispel").
