- 2026-07-19: Live sync is a contentless per-project broadcast ping, not a data channel. After any write, the server posts an empty ping to `belin:project:<id>` via the Supabase realtime broadcast REST endpoint; open clients re-run their server components through their own authorized reads. Nothing crosses the channel, so there is no data to leak and no client-side merge to get wrong; the server stays the single source of truth. The primary REST endpoint was verified working (HTTP 202); the documented fallback (realtime.send inside the RPCs plus triggers) exists (realtime.send confirmed present) but is not needed. Accepted debt: the channel is public and its topic is derivable from the project UUID, which already appears in signed photo URL paths, so a holder of the anon key plus a UUID could both listen for and inject pings. A forged ping only makes clients re-fetch through authorized reads (no data exposure, no writes) and the client debounce caps the rate, so this is a bounded refresh-amplification surface, accepted for the PoC. Private channels with realtime authorization arrive with real auth in phase 3.

- 2026-07-19: The EPC "add material item" control on the dashboard is an explicit stopgap, not the product's data path. Design law 2 is zero manual entry: the real Stückliste will be extracted from the uploaded plan PDF, and the EPC reviews it. The manual add exists so the crew re-check loop is demonstrable and testable before that extraction is built, and so the founder can trigger the live re-check prompt during the demo. The demo narration frames it as "until your Stückliste comes straight from your plan PDF". Editing and deleting lines are deliberately out of scope for the PoC.
- 2026-07-19: The material check first-gate is escapable ("Material še ni prispel"). It writes a truthful empty check, unlocks daily reporting, and notifies the EPC, with a standing re-check prompt until a real check covers the list. This amends the 2026-07-17 hard-gate decision: a hard gate locked out day-one crews doing reportable setup work before any delivery, and the only workaround wrote a false "all missing" alarm. The escape preserves the decision's intent (the EPC learns on day one what did or did not arrive) without the lockout. The gate is enforced server-side in submitDailyReport, not just in the UI.

- 2026-07-19: Material check model decided (the question deferred from the 2026-07-17 audit, finding M13). One Stückliste per project, which the sub receives. If the EPC adds items later, the sub is prompted to check that the additions arrived, so the check is a living record rather than a single frozen event. The check carries two document attachments: a photo of the delivered material, and the delivery note (dobavnica or prevzemni list). Reason: founder decision from field practice. Deliveries arrive in waves, so one frozen check stops being true after the second truck, and the delivery note is the document that actually settles disputes about what was supplied. The safe default already in the database (history log with a latest-lookup index) matches this, so nothing needs redoing.
- 2026-07-19: The Belin mark is one shape everywhere: 3 cells wide, 4 tall, columns rising 1, 2, 3 gold cells from the bottom. - 2026-07-19: The EPC dashboard's second chart shows daily tempo (percentage points gained per working day against the flat pace the plan requires), not cumulative progress. Non-working days never appear on the axis, a reported zero is visually distinct from a missing report, and the projection line and deadline buffer band were removed from the chart (the buffer survives as the badge). Reason: founder proposal, confirmed by research. Cumulative progress was already the hero number directly above the chart, and two controlled studies (MeasuringU, n=50 and n=51) found cumulative charts are misread 82 to 88 percent of the time when the question is rate of change, with the read direction flipping versus the same data shown per period. A tempo view also immediately exposed a pace decline the cumulative curve concealed. Considered and rejected: a days-ahead/behind delta chart, which the research ranked first, because Belin exists to document what a subcontractor did on a given day and a delta line abstracts a weak day away.

- 2026-07-20: v1 master plan authored (docs/superpowers/plans/2026-07-20-v1-master-plan.md): 27 tasks in 9 parts covering accounts with custom magic-link auth, K2 parser, PDF engine port, naročilnica with hash-bound acceptance, notifications, incidents, requests, Regiestunden, change orders, finalization with acceptance protocol and reverse-charge-safe invoice, portfolio, expanded landing, translation pass, staged four-phase demo and security cleanup. - 2026-07-20: The K2 parser is structured as a leaf module of primitives (lib/k2/k2-core.ts) with lib/k2/k2-shared.ts as a pure public facade over it, rather than the single shared module the parser plan specified. Reason: the plan had k2-shared.ts composing the very modules that import it, which closes an import cycle in foundation code. The split keeps the module graph acyclic while leaving the public entry points (parseK2Text, parseK2Pdf, parseK2Xlsx, all imported from @/lib/k2/k2-shared) exactly as every consumer expects, so Task C2's contract is untouched. Also decided in the same pass: no file under lib/k2 imports "server-only", deliberately breaking the repo's usual server-lib convention, because these modules are Node-safe pure logic that the test suite and the k2:try harness import under plain Node, where that import throws; they hold no secrets and read no environment.
- 2026-07-20: A K2 parse never fails, it warns. The only condition that returns ok false is a missing footer fingerprint, which means the file is not a K2 report and the wizard offers manual entry. Everything else (no article list, per-roof lists instead of a project total, a weight that disagrees with the printed Summe, unresolvable project metadata) comes back as a warning code beside a usable result. Reason: design law 2. The EPC reviews and corrects rather than typing from scratch, and a partly understood plan is worth far more than an error message. The parser emits codes, not i18n keys, so it never has to know about translation namespaces.
- 2026-07-20: The project wizard is PLAN FIRST: step one is the K2 upload, not a form. Everything the review screen shows is prefilled from the plan and editable, and the article list becomes the project's material list directly. Reason: design law 2 (stupidly easy for the EPC, zero manual data entry, the EPC reviews instead of types). The order is the feature; asking for a project name before the file would waste the fact that the file already holds the answers. A file that is not recognized as K2 does not block anything: the same review screen opens empty and the EPC types, so the wizard has exactly one path.
- 2026-07-20: A project's country comes from the uploaded plan when the plan names one, and only falls back to the EPC organization's own country. Reason: a Slovenian EPC routinely builds in Germany or Austria, and country drives the VAT mode on every document that follows, so inheriting the EPC's country by default would quietly produce wrong invoices. The address parser recognizes the country spellings K2 actually prints in German and Slovenian.
- 2026-07-20: Creating a project from a reviewed plan goes through one transactional Postgres function (create_project_from_review) that writes the project, its access tokens and every material line, backfills plan_imports, validates that a chosen sub org is really a sub, and refuses a second commit of the same import. Reason: the same rule as submit_daily_report and submit_material_check. A partial write here would leave the EPC looking at a project whose material list silently lost rows, and a double submit would create twin projects. Sub tokens are minted only when a sub is actually attached, because a token resolving to no sub organization would produce an actor with no org.
