- K2 hardening, Task H3: the breadcrumb grammar (lib/k2/k2-crumbs.ts), which retires the word "Dach" from the parser entirely. K2 stopped calling roofs Dach: the 3.2.7x era says "Bereich", the English export says "Area", and a planner can type anything they like, which is how four of the founder's five real reports came back with zero roofs. Areas are now ENUMERATED from the breadcrumb K2 prints on every content page, whose SHAPE is stable across every era and language even though its words are not: a bare list term is the project total, a list term beside another segment is that segment's area, and statics, results and assembly crumbs name their area in a fixed position. Whatever sits in those positions IS the area name, so a renamed area cannot break it. Two rules earn their place: single segment crumbs are never areas (they collide with project names, reseller URLs and section intros, and would invent roofs that do not exist), and the roofs section segment is stripped from assembly crumbs as well as list crumbs, because the older era nests them and without the strip forum1 enumerates a bogus fourth area, the counts stop matching the overview rows, and every roof silently loses its panel count. 20 tests pin the classifier in both languages plus the area list of all ten fixtures.

- K2 parser, Task K5: lib/k2/k2-metadata.ts, 8 tests. The hard fact this module exists to absorb is that K2's two column layout reaches pdf.js in two different text orders: some reports emit "Windlastzone 2" on one line, others emit a run of bare labels followed by a run of bare values. Both are attempted, inline first, and positional pairing is accepted ONLY when the two runs are exactly the same length, so a layout this parser has not seen leaves fields null instead of shifting every value by one. Section headings (Lasten, Projektinformation, Materialeigenschaften, Dächer) are skipped inside the label run: they neither count nor break it. Block pairing is forbidden on the cover page, because forum1's cover is block mode and pairing it would marry Gesellschaft to the project subtitle. Roof kWp is computed from the roof's OWN module wattage times its count rather than parsed from the printed cell, because forum1 carries a 455 Wp module on Dach 1 and a 460 Wp module on Dach 3 and the kWp cell uses a period decimal where the Summe row uses a comma. HARDENING beyond the plan, found by a synthetic test rather than a fixture: the value run now stops at page furniture (the breadcrumb anchor, the footer, the vendor URL). Without that guard a page carrying more labels than values silently absorbs the footer as a value and shifts every field; no fixture triggers it, a future layout would.
- K2 parser, Task K4: lib/k2/k2-articles.ts, extractArticleLists and selectItems, 10 tests. A page is an article page when a line matches the row pattern (position, 7 digit article number, verbatim name, quantity, comma decimal weight in kg); the name is never normalized, so "Wood screw 8×160" keeps its unicode multiplication sign and "SingleRail 36; 4.40 m" keeps the semicolon and the period decimal. Which list a page belongs to is decided by the BREADCRUMB after the exact line "| Connecting Strength": forum1 carries three lists that are otherwise textually identical in shape, two per roof and one project total, and only the breadcrumb distinguishes them. A project total wins outright; with only per roof lists the items are summed per article number and flagged per_roof_fallback, because the EPC is then reading a number this parser computed rather than one K2 printed. The printed Summe is checked against the rows with a tolerance of 0.05 kg per row plus 0.2 (row weights are printed rounded to 0,1 kg, so the error accumulates with row count); a disagreement emits weight_mismatch and never fails the parse.
